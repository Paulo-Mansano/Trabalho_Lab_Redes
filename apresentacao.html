1. Visão geral e topologia

O trabalho prova, em etapas, por que um protocolo de aplicação sem proteção é vulnerável. Criamos um protocolo de login próprio (SLAP) e o atacamos:

FaseO que fazQuebra que demonstra
1Sniffer passivo lê o tráfegoConfidencialidade (lê a senha)
2Proxy MITM lê e altera o tráfegoIntegridade e autenticação
3TLS + certificadoDefesa: o ataque passa a falhar
Rede Interna VirtualBox "labredes" (modo promíscuo: Permitir Tudo) ┌───────────────────────────────────────────────────────────────┐ VM-cliente ───────────► switch virtual ◄─────────── VM-servidor 10.10.10.20 │ 10.10.10.10:7070 ▼ VM-observador 10.10.10.30 Fase 1: sniffer (escuta) Fase 2: proxy (intercepta) └───────────────────────────────────────────────────────────────┘
O tripé da segurança
Confidencialidade (ninguém lê) — quebrada na Fase 1. Integridade (ninguém altera) e Autenticação (é quem diz ser) — quebradas na Fase 2. Todas defendidas na Fase 3 com TLS.

2. Teoria: as camadas

Quando o cliente envia PASS senha123, essa string é encapsulada em camadas, cada uma com seu cabeçalho:

┌─────────────────────────────────────────────────────────────┐ │ Cabeçalho IP │ Cabeçalho TCP │ "PASS senha123\r\n" │ │ (origem/dest)│ (portas/seq) │ ← PAYLOAD DA APLICAÇÃO (SLAP) │ └─────────────────────────────────────────────────────────────┘ 20 bytes 20+ bytes dados em TEXTO CLARO
  • Aplicação (SLAP): o texto que criamos. Sem cifragem, viaja legível.
  • Transporte (TCP): entrega confiável e ordenada; identifica a conexão pelas portas (7070).
  • Rede (IP): endereça por IP de origem/destino.
  • Enlace (Ethernet): entrega quadro a quadro na rede local, por MAC.

O sniffer (Fase 1) faz o caminho inverso — desencapsula: lê o cabeçalho IP para achar onde o TCP começa, lê o TCP para achar o payload, e então lê o texto SLAP.

3. O protocolo SLAP

SLAP (Simple Login Access Protocol): texto ASCII, uma linha por mensagem terminada em \r\n, inspirado no FTP (códigos 220/331/230/530/221).

Servidor Cliente │──── 220 slap-server pronto ────►│ │◄────────── USER aluno ──────────│ │──── 331 senha requerida ───────►│ │◄────────── PASS senha123 ───────│ ← credencial em texto claro │──── 230 login bem-sucedido ────►│ (ou 530 se inválido) │◄────────── QUIT ────────────────│ │──── 221 ate mais ──────────────►│
Fase 1 — Escuta passiva

4. O servidor fase1/servidor/servidor.py

def main():
    servidor = socket.socket(socket.AF_INET, socket.SOCK_STREAM)  # IPv4 + TCP
    servidor.bind((host, porta))        # reserva o 10.10.10.10:7070
    servidor.listen()
    while True:
        conexao, endereco = servidor.accept()   # bloqueia até chegar um cliente
        threading.Thread(target=atender_cliente,
                         args=(conexao, endereco), daemon=True).start()

Teoria: SOCK_STREAM = TCP. O padrão bind+listen+accept define um servidor TCP; cada conexão roda em uma thread, atendendo vários clientes ao mesmo tempo.

def atender_cliente(conexao, endereco):
    enviar(conexao, "220 slap-server pronto")
    linha = receber_linha(conexao)              # espera "USER ..."
    usuario = linha[5:].strip()
    enviar(conexao, "331 senha requerida")
    linha = receber_linha(conexao)              # espera "PASS ..."
    senha = linha[5:].strip()
    if USUARIOS.get(usuario) == senha:         # credenciais em texto claro (de propósito)
        enviar(conexao, "230 login bem-sucedido")
    else:
        enviar(conexao, "530 usuario ou senha invalidos")

5. O cliente fase1/cliente/cliente.py

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as conexao:
    conexao.connect((host, porta))              # conecta ao servidor (ou ao proxy, na Fase 2)
    enviar(conexao, f"USER {usuario}")
    print(">", "PASS " + "*" * len(senha))  # mascara na TELA apenas
    enviar(conexao, f"PASS {senha}")              # mas envia a senha REAL na rede
Detalhe que impressiona
O cliente mostra PASS ********, mas envia PASS senha123 em claro. A máscara é só cosmética — o atacante captura a senha real.

6. O sniffer fase1/observador/sniffer.py

def montar_socket_raw(ip_interface):
    s = socket.socket(socket.AF_INET, socket.SOCK_RAW, socket.IPPROTO_IP)
    s.bind((ip_interface, 0))                 # liga à placa do observador
    s.ioctl(socket.SIO_RCVALL, socket.RCVALL_ON)  # "me entregue TODOS os pacotes IP"
    return s

Teoria: um socket comum só recebe o que é endereçado a ele. Um socket raw (SOCK_RAW) entrega o pacote inteiro, com os cabeçalhos IP/TCP, para o programa interpretar. No Windows, SIO_RCVALL coloca a placa em modo de recepção total (promíscuo) — por isso exige Administrador.

def interpretar_ip(pacote):
    versao_ihl, _, _, _, _, ttl, protocolo, _, origem, destino = \
        struct.unpack("!BBHHHBBH4s4s", pacote[:20])
    tamanho_cabecalho = (versao_ihl & 0x0F) * 4   # IHL: onde o TCP começa
    return {"protocolo": protocolo, ...}

Depois o código lê o cabeçalho TCP (as portas e o data offset), soma os tamanhos para achar o início do payload, filtra a porta 7070 e revela USER/PASS. Resultado real:

10.10.10.20:49673 -> 10.10.10.10:7070  *** CREDENCIAL CAPTURADA *** 'USER aluno'
10.10.10.20:49673 -> 10.10.10.10:7070  *** CREDENCIAL CAPTURADA *** 'PASS senha123'

7. Por que a escuta funciona (e por que quase não funcionou)

Duas camadas cooperam: (1) o modo promíscuo da rede virtual espelha todos os quadros para o observador; (2) o socket raw + SIO_RCVALL entrega tudo ao programa.

A pegadinha
Com o Firewall do Windows ligado na VM-observador, o Defender descarta os pacotes antes do socket raw e o sniffer captura zero. Solução: netsh advfirewall set allprofiles state off. Se travar na demo, é quase sempre isso.
Fase 2 — MITM ativo

8. O que é um Man-in-the-Middle (MITM)

Na Fase 1 o atacante só ouvia. Na Fase 2 ele entra no meio do caminho: o cliente conversa com o atacante achando que é o servidor, e o atacante repassa (e altera) para o servidor real. Ele vê e controla os dois lados.

Fase 1 (passivo): cliente ───────────────► servidor (só escuta) Fase 2 (ativo): cliente ──► PROXY MITM ──► servidor lê e ALTERA

Como redirecionamos sem hackear nada: o cliente já recebe o IP de destino por parâmetro. Basta apontá-lo ao proxy (10.10.10.30) em vez do servidor — é o "redirecionamento por configuração do serviço" que o enunciado pede. Cliente e servidor não mudam.

9. O proxy MITM fase2/proxy/proxy_mitm.py

9.1 Aceitar o cliente e abrir o servidor real

while True:
    cliente_sock, endereco = escuta.accept()        # o cliente conecta no proxy
    threading.Thread(target=atender_sessao,          # 1 thread por sessão -> concorrência
                     args=(cliente_sock, endereco, destino_servidor, regras),
                     daemon=True).start()
def atender_sessao(cliente_sock, endereco, destino_servidor, regras):
    servidor_sock = socket.create_connection(destino_servidor)  # proxy abre o servidor real
    # duas threads de relay: uma por sentido (full-duplex)
    t_cs = threading.Thread(target=repassar,
              args=(cliente_sock, servidor_sock, "C->S", regras[0], sid, fechar), daemon=True)
    t_sc = threading.Thread(target=repassar,
              args=(servidor_sock, cliente_sock, "S->C", regras[1], sid, fechar), daemon=True)
    t_cs.start(); t_sc.start(); t_cs.join(); t_sc.join()

9.2 Repassar e, se quiser, ALTERAR cada linha

def repassar(origem, destino, rotulo, regras, sid, fechar):
    while True:
        linha = ler_linha(origem)
        if not linha: break
        nova = aplicar_regras(linha, regras)        # aqui o conteúdo é adulterado
        if nova != linha:
            log(sid, rotulo, f"*** MODIFICADO *** {linha!r} -> {nova!r}")
        destino.sendall(nova)                        # encaminha (já alterado)
def aplicar_regras(linha, regras):
    for alvo, troca in regras:
        if alvo in linha:
            linha = linha.replace(alvo, troca)
    return linha

# Demo padrão: TROCA DE IDENTIDADE em trânsito
REGRAS_C2S = [
    (b"USER aluno\r\n",    b"USER professor\r\n"),
    (b"PASS senha123\r\n", b"PASS acesso2026\r\n"),
]

Teoria: como o proxy fica no meio e o protocolo não tem proteção de integridade, ele pode trocar qualquer mensagem. As regras ficam isoladas no topo do arquivo — fáceis de editar. Há uma regra alternativa comentada que forja a resposta do servidor (530 → 230).

10. Concorrência e regiões críticas

O proxy atende várias sessões ao mesmo tempo (requisito da fase). Modelo de threads:

Thread principal ── accept() em laço └──► Thread de sessão (1 por cliente) ├──► Thread de relay C->S (cliente → servidor) └──► Thread de relay S->C (servidor → cliente)

Cada sessão só mexe nos próprios sockets — nada é compartilhado entre sessões. O único estado compartilhado entre threads são (a) o contador de sessões e (b) a saída do log. Ambos protegidos por Lock (as regiões críticas):

_lock_contador = threading.Lock()
_contador_sessoes = 0

def proximo_id():
    global _contador_sessoes
    with _lock_contador:            # incremento atômico (senão IDs repetiriam)
        _contador_sessoes += 1
        return _contador_sessoes
  • Por que o lock no contador? contador += 1 não é atômico; duas sessões ao mesmo tempo poderiam gerar o mesmo ID.
  • Por que o lock no log? Sem ele, print de threads diferentes embaralha os caracteres na mesma linha.
  • As regras não precisam de lock: são só leitura após a inicialização.
  • Sem deadlock: os dois locks são "folha" (nunca um segura o outro) e ficam presos por um instante.

Detalhes completos em fase2/CONCORRENCIA.md.

11. A adulteração — o clímax da Fase 2

O cliente faz login como aluno/senha123, mas o proxy troca a identidade em trânsito. Nenhum dos dois percebe:

# PROXY (adulterando)
[sessao 01][C->S] *** MODIFICADO *** b'USER aluno\r\n'   -> b'USER professor\r\n'
[sessao 01][C->S] *** MODIFICADO *** b'PASS senha123\r\n' -> b'PASS acesso2026\r\n'

# CLIENTE (acredita ser aluno)
> USER aluno
< 230 login bem-sucedido

# SERVIDOR (autenticou professor!)
Login OK: usuario='professor' de 10.10.10.20
O que isso prova
A identidade da sessão foi trocada sem o cliente nem o servidor detectarem — quebra combinada de integridade (a mensagem foi alterada) e autenticação (o servidor autenticou alguém que o cliente nunca pediu).

13. Perguntas prováveis da banca

Clique para revelar. Treine em voz alta.

Qual a diferença entre um socket comum e um socket raw?
O comum (TCP/UDP) entrega só os dados endereçados ao programa; o SO já processou IP/TCP. O raw entrega o pacote inteiro com os cabeçalhos, para o programa interpretar — é o que permite ler tráfego alheio (Fase 1).
O que é um ataque man-in-the-middle?
O atacante se posiciona entre as duas pontas: cada lado pensa que fala diretamente com o outro, mas o tráfego passa pelo atacante, que pode ler e alterar. No nosso caso, redirecionamos o cliente para o proxy.
Como o proxy consegue alterar a mensagem sem ninguém notar?
Porque o SLAP não tem integridade (nada assina/verifica a mensagem) nem autenticação das pontas. O proxy lê linha a linha, troca o conteúdo (ex.: USER aluno → USER professor) e repassa. Cliente e servidor aceitam como legítimo.
Como o proxy atende vários clientes ao mesmo tempo?
Uma thread por conexão (no accept), e dentro de cada sessão duas threads de relay (um sentido cada). As sessões são independentes; o estado compartilhado (contador e log) é protegido por Lock.
O que são as "regiões críticas" do proxy?
Trechos que mexem em estado compartilhado entre threads: o contador de sessões e a saída de log. Cada um é protegido por um threading.Lock para evitar corrida (IDs repetidos / linhas embaralhadas).
Por que escolheram TCP e não UDP?
TCP dá entrega confiável e ordenada (base de um login real como o FTP) e prepara o terreno para o proxy e para o TLS da Fase 3, que roda sobre TCP.
Isso não é uma ferramenta de ataque ilegal?
É uma prova de conceito acadêmica, só dentro da rede isolada do grupo (ou em localhost), cujo propósito declarado é fundamentar a defesa da Fase 3.
Como a Fase 3 impede esses ataques?
Com TLS: o conteúdo é cifrado (o sniffer não lê, o proxy não altera de forma coerente) e o certificado do servidor autentica a ponta, impedindo o MITM de se passar pelo servidor — a adulteração é detectada no handshake.
